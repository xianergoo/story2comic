# 从后端工程师到 AI 开发工程师的演进路线

> 日期：2026-06-08 | 状态：已落盘 | 目标主体：当前主仓 `auto_drama`

## 一、本文目标

本文不是单纯讨论 `auto_drama` 该做哪些功能，而是明确回答一个更重要的问题：

**如何把 `auto_drama` 变成个人 AI 工程训练场，帮助开发者从后端工程师逐步转型为 AI 开发工程师。**

这里的“AI 开发工程师”不是只会调用模型接口的人，而是能够：

1. 设计 agent
2. 编排 AI workflow
3. 构建可评估的多模态系统
4. 让 AI 能力变成可交互、可迭代、可观测的产品能力

## 二、当前背景重新定义

### 1. `auto_drama` 的真实价值

`auto_drama` 不是现成成熟平台，但它是一个非常适合继续迭代的主仓，因为它已经具备：

- 清晰的 Go API + Vue SPA 架构
- 结构化 SSE 实时事件体系
- 可运行的异步生成闭环
- 低成本试错和快速修改能力

因此，`auto_drama` 最重要的身份不是“现成平台”，而是：

**一个可持续演进的 AI 产品实验场。**

### 2. 本地 huobao 三仓的真实价值

本地 huobao 三仓不是普通参考代码，而是更早、且上过生产环境的前代体系。

因此它的参考意义要重新提升：

- 它提供了更强的 agent 设计经验
- 它提供了更成熟的多模态生产经验
- 它提供了更接近真实平台的工作流与中台经验

后续不应该把它当成“是否整体迁移”的对象，而应该把它当成：

**能力来源和方法论来源。**

### 3. 当前阶段的现实目标

当前不是直接做完整短剧平台的时候，而是先完成：

**快速可交互、可用的文生图功能。**

这意味着后续优先级必须服从两个原则：

1. 优先做对当前产品有直接价值的能力
2. 优先做能训练 AI 工程能力的方法性能力

## 三、转型过程中最该强化的四类能力

## 1. Agent 设计能力

这是从后端工程师迈向 AI 开发工程师最核心的能力。

要重点训练的不是“如何多调几个模型”，而是：

- 何时应该使用 agent
- 何时应该拆成 tool
- 一个 agent 的输入、输出、状态边界如何定义
- 一个 agent 是否需要 checkpoint / interrupt / resume
- agent 如何与业务对象绑定
- 多个 agent 如何分工，而不是做一个万能 agent

对当前 `auto_drama` 来说，最适合训练的不是大而全 agent，而是小而清楚的角色化 agent，例如：

1. `story_analyzer`
2. `character_extractor`
3. `scene_extractor`
4. `image_prompt_generator`
5. `consistency_checker`

这些 agent 都可以从 huobao 的思路中吸收经验，但应以 `auto_drama` 当前的产品目标重新落地。

## 2. Workflow 编排能力

很多后端工程师可以写 service，但不会真正设计 AI workflow。

AI 开发工程师需要掌握的是：

- 多阶段任务拆分
- 中间结果持久化
- 可恢复执行
- 失败重试
- 人工介入节点
- 实时状态反馈
- 任务编排与业务对象的对齐方式

`auto_drama` 当前已经有：

- task queue
- SSE 事件流
- 分阶段生成链路

这正是继续升级 workflow 能力的良好基础。

## 3. Eval 与可观测能力

这是最容易被忽略、但最能拉开水平差距的一层。

如果没有 eval 和 tracing，开发者很容易停留在：

- 试一试 prompt
- 看起来还行
- 失败了就重跑

而不是进入真正的系统化优化。

后续应该主动建设：

- prompt/version 记录
- tool 调用日志
- agent 执行轨迹
- 失败原因分类
- 输出质量人工打分
- 样本库与 benchmark case

只要这层能力开始建立，开发方式就会从“拍脑袋试模型”转向“可评估地做 AI 系统”。

## 4. 多模态产品化能力

你的目标不是做一个聊天机器人，而是做内容生产产品。

因此需要逐步掌握：

- 文本生成
- 图像生成
- 提示词构造
- 角色/场景一致性
- 资产沉淀
- 视频前置能力
- 后处理与合成前链路

本地 huobao 三仓在这方面的经验，比当前 `auto_drama` 丰富得多，因此后续值得优先吸收其多模态抽象思路，而不是重复从零探索。

## 5. AI 生成内容的人审能力

由于当前大量文档、分析、设计和改进建议都可能由 AI 辅助生成，因此还必须额外训练一种常被忽略的能力：

**对 AI 输出进行结构化复核和风险判断的能力。**

这类能力不属于传统后端开发的核心训练项，但对 AI 开发工程师非常重要。

需要重点关注的不是“AI 写得像不像”，而是：

- 结论是否建立在真实上下文上
- 是否偷换了目标
- 是否把原型结论误写成生产结论
- 是否把参考项目的局部经验误当成通用最佳实践
- 是否遗漏了真正影响产品路线的约束条件

换句话说，后续不能把 AI 当成自动产出正确方案的工具，而必须把它当成：

**高效率候选方案生成器，而最终判断权仍必须掌握在自己手里。**

## 四、`auto_drama` 应该扮演什么角色

后续 `auto_drama` 不应只是一个要不断加功能的业务仓库，而应该被有意识地当成：

**AI 工程训练场 + 产品实验场 + 方法论沉淀场。**

这意味着每次做功能时，都最好用三层视角去判断价值：

### 1. 产品价值

这个能力是否直接提升“可交互的文生图可用性”？

### 2. 工程价值

这个能力是否能训练 agent / workflow / eval / multimodal 抽象能力？

### 3. 方法论价值

这个能力做完后，是否能沉淀成以后可复用的设计模式或判断标准？

如果一个改动只提升普通后端体验，但对上述三者帮助很弱，就不应排到前面。

## 五、现阶段不应优先做的事

为了避免时间被稀释，以下事情现阶段不应排到最高优先级：

### 1. 过早做重型架构拆分

例如：

- 一开始就拆独立 agent 服务
- 一开始就追求多进程调度
- 一开始就追求复杂微服务边界

这些事情未来可能要做，但当前还不是最优先训练点。

### 2. 过早追求完整短剧生产平台

当前还不应一口气把：

- 分镜
- 视频
- 配音
- 合成
- 时间线

全部推进到主链路。

这会把焦点从“形成 AI 工程能力”转移到“处理大量平台复杂度”。

### 3. 过多投入普通后端型工作

例如纯 CRUD 扩展、纯常规接口清理、与 AI 主链路无关的小修补，不应该持续抢占最重要的时间。

## 六、AI 生成文档与改进时，你需要额外关注什么

由于后续很多文档、设计、分析乃至代码改进都可能由 AI 辅助完成，因此建议你对以下内容保持固定审查意识。

## 1. 目标是否被悄悄改写

这是最常见的问题之一。

例如你当前真正目标是：

- 先完成快速可交互的文生图能力
- 借项目训练 agent 开发能力

但 AI 很容易把目标悄悄改成：

- 完整短剧平台建设
- 一次性重构成通用 agent 平台
- 追求架构完美而不是当前可用性

因此凡是 AI 产出需求分析、方案、计划时，都应先检查：

**这份内容是否仍然服务当前阶段目标，而不是自动滑向更大、更全、更远的方向。**

## 2. 结论是否超出了证据边界

AI 很容易把“看上去合理”写成“已经确认正确”。

你需要额外关注：

- 哪些结论来自真实代码
- 哪些只是基于目录结构的推测
- 哪些是经验判断
- 哪些还缺运行验证

特别是在分析 huobao 或设计 agent 演进路线时，要警惕 AI 把“推演”写成“事实”。

## 3. 方案是否过度理想化

AI 常见倾向是：

- 喜欢给出结构漂亮的方案
- 喜欢一次性做完整分层
- 喜欢默认后续能力都会顺利补齐

但你的真实约束是：

- 当前主项目是 `auto_drama`
- 当前先做文生图可用链路
- 当前主要目标之一是训练自己

所以你需要反复检查：

**这个方案是不是很好看，但对当前你来说太重、太慢、太远。**

## 4. prompt、agent、tool 边界是否被写得过于模糊

AI 非常容易给出一些听起来正确、但边界并不清晰的设计描述，例如：

- 增加一个 agent 来处理内容
- 增加若干 tools 支撑生成
- 做一个 workflow 管理执行过程

这些话如果不继续追问，很容易变成空设计。

因此你需要额外关注：

- 这个 agent 到底处理什么输入
- 产出什么结构
- 谁来调用它
- tool 的输入输出是什么
- 状态如何持久化
- 哪一步失败时如何恢复

只要这些问题答不清，这份设计就还不能进入高可信执行阶段。

## 5. AI 生成代码时是否引入了“能跑但不适合演进”的实现

很多 AI 代码在短期内看似可用，但长期会埋下问题，例如：

- 把 prompt 写死在业务函数里
- 把事件类型散落在多个地方
- 把 agent 状态耦合在 handler 中
- 用大量字符串约定代替清晰模型
- 为了快而把调试逻辑直接混进生产逻辑

所以你应额外关注：

- 结构是否支持后续演进
- 是否能被观察和调试
- 是否容易替换 provider / prompt / tool
- 是否把临时方案伪装成正式设计

## 6. AI 生成文档时是否缺少“人工判断点”

很多 AI 生成文档会把路线写得很顺，但不会主动告诉你：

- 哪里需要停下来复盘
- 哪些结论必须自己拍板
- 哪些节点不适合继续让 AI 自动推进

所以后续凡是路线图、方案文档、计划文档，都最好要求加入：

- 人工决策点
- 人工复核点
- 需要运行验证的点
- 不确定性说明

## 七、建议设置的固定提醒机制

为了避免 AI 生成内容把你带偏，建议后续在生成关键内容时，固定提醒自己检查以下事项。

## 1. 在生成需求分析时提醒

需要额外提醒自己检查：

- 当前目标是否被改写
- 是否混入下阶段目标
- 是否把“长期理想”放到了“当前优先级”前面

## 2. 在生成技术方案时提醒

需要额外提醒自己检查：

- 是否过度设计
- 是否真的适合当前主仓
- 是否能服务文生图主链路
- agent / tool / workflow 边界是否清楚

## 3. 在生成实现计划时提醒

需要额外提醒自己检查：

- 计划是否可分阶段完成
- 是否能先交付一个可用闭环
- 是否把验证步骤写清楚
- 是否把评估和 tracing 忽略掉了

## 4. 在生成代码时提醒

需要额外提醒自己检查：

- 是否把临时逻辑混入核心结构
- 是否把 prompt、状态、事件协议写散了
- 是否保留了后续 agent 演进空间
- 是否只是在“为了快能跑”，而不是“可持续迭代”

## 5. 在生成阶段总结时提醒

需要额外提醒自己检查：

- 本阶段真正学到了什么
- 哪些是 AI 给出的建议，哪些是自己验证过的结论
- 哪些能力已经形成方法论
- 哪些问题还只是“看起来解决了”

## 八、应该优先做什么

结合你的目标，我建议把后续重点分成三个阶段。

## 阶段一：把 `auto_drama` 做成可交互的文生图产品

这是短期最重要阶段。

### 目标

不是“能生成图片”就算完成，而是：

- 输入清楚
- 生成过程可见
- 结果可查看
- 失败可重试
- 多次结果可比较
- 中间分析步骤可观察

### 这一阶段最应该训练的能力

- 最小 AI 产品闭环能力
- 生成链路可视化能力
- agent 前置分析可用性设计能力

### 这一阶段建议优先补的能力

1. 文生图主流程入口
2. 输入文本分析步骤展示
3. prompt 生成过程展示
4. 图片生成结果列表
5. 重试 / 再生成 / 对比
6. 生成事件流日志

在这一阶段，凡是 AI 生成需求、方案或代码时，应额外提醒自己重点复核：

- 这是不是仍然围绕文生图主链路
- 是否偷偷扩成了完整平台建设
- 用户是否真的能感知到“可交互”和“可用”

## 阶段二：把 huobao 的 agent 思想吸收到 `auto_drama`

这里的重点不是迁移代码，而是迁移能力模型。

### 建议吸收的核心点

1. supervisor + tools 的组织方式
2. checkpoint / resume 设计
3. 小 agent 角色化拆分
4. 任务状态机设计
5. 多模态 provider 抽象

### 这一阶段最应该训练的能力

- agent runtime 设计
- tool calling 设计
- agent 与业务模型绑定
- 多阶段 workflow 编排

在这一阶段，凡是 AI 生成 agent 设计或 workflow 方案时，应额外提醒自己重点复核：

- 边界是否清楚
- 输入输出是否结构化
- 哪些步骤需要 checkpoint
- 哪些恢复机制是真正可执行的，而不是概念描述

## 阶段三：逐步扩展到短剧生产链路

只有前两个阶段稳定后，才适合进入这一阶段。

### 建议扩展方向

1. 角色一致性
2. 场景拆分
3. 分镜草图
4. 资产模型
5. 视频前置能力
6. 审核 / checkpoint 工作流

### 这一阶段最应该训练的能力

- 多 agent 协作
- 多模态生产系统设计
- 平台化思维

在这一阶段，凡是 AI 生成平台化路线或多模态设计时，应额外提醒自己重点复核：

- 是否超出当前阶段资源和精力
- 是否有足够的评估与观测支撑
- 是否会把训练目标重新变成单纯平台堆功能

## 九、建议优先吸收 huobao 的哪些能力

不是所有能力都应同等优先。建议按以下顺序吸收。

### 优先级最高

1. agent 角色拆分思路
2. tool 边界设计
3. checkpoint / resume 思路
4. 多模态 provider 抽象

### 第二优先级

1. 资产沉淀方式
2. 任务流与状态机
3. 图像 / 视频 / 合成前的中间对象设计

### 第三优先级

1. 更复杂的独立 agent 服务化
2. 更完整的短剧平台工作台
3. 更重的生产编排体系

## 十、30 / 60 / 90 天建议路线

## 1. 30 天目标

重点：先把“文生图可交互闭环”打通。

建议输出：

1. 一个可稳定演示的文生图流程
2. 一个最小 agent 链路
3. 一套生成过程事件可视化
4. 一组可复盘的失败 case

这一阶段不要追求完整平台，而要追求：

**看得见、能重试、可复盘。**

此阶段建议固定提醒：

- 任何 AI 产出都先检查是否有助于可用闭环
- 任何“很完整的大方案”都先降级成最小可验证方案

## 2. 60 天目标

重点：把 agent 从“有调用”升级到“有结构”。

建议输出：

1. 角色化 agent 划分
2. tool 调用日志
3. prompt/version 管理雏形
4. checkpoint 或人工确认节点原型
5. 简单评估样本库

这一阶段的重点不是功能数量，而是：

**让 AI 行为变得可分析、可管理。**

此阶段建议固定提醒：

- 所有 agent 设计都必须补输入输出定义
- 所有 workflow 设计都必须补失败与恢复说明
- 所有 prompt 优化都尽量留下版本和对比依据

## 3. 90 天目标

重点：建立自己的 AI 工程方法论雏形。

建议输出：

1. 对 agent 边界有稳定判断标准
2. 对 workflow 拆分有稳定设计套路
3. 对图像生成与一致性有自己的评估方法
4. 开始具备向短剧上游结构演进的基础

这一阶段的目标不是“产品已经很大”，而是：

**你已经具备独立设计 AI 系统的能力框架。**

此阶段建议固定提醒：

- 区分哪些是方法论，哪些只是个案成功
- 区分哪些能力已内化，哪些仍依赖 AI 帮你组织思路

## 十一、未来做每个需求时都该问自己的问题

为了确保方向不偏，后续每做一个新需求，都建议先问这几个问题：

1. 这个需求是增强普通后端能力，还是增强 AI 工程能力？
2. 它是否能训练我对 agent / workflow / eval 的判断？
3. 这个能力是否真的服务当前“可交互文生图”目标？
4. 它是否值得沉淀成复用模式或文档？
5. 现在做它，是否比补 tracing / eval / workflow 更值？

如果答案偏弱，就不该优先。

## 十二、建议长期保持的人工复核清单

后续只要是 AI 生成的文档、分析、设计、计划或代码，都建议你至少检查以下清单：

1. 目标有没有被改写
2. 结论有没有超出证据边界
3. 方案有没有过度设计
4. agent / tool / workflow 边界是否足够清楚
5. 是否保留了后续演进空间
6. 是否写清了人工决策点和验证点
7. 是否真的服务当前阶段目标

如果这 7 条里有 2 到 3 条答不清，就不建议直接继续推进下一步。

## 十三、最终建议

如果把“从后端工程师转型为 AI 开发工程师”作为第一目标，那么当前最合理的路线不是尽快把 `auto_drama` 做成一个复杂平台，而是：

**先把 `auto_drama` 做成一个高频迭代、可交互、可观测的文生图产品实验场，再有意识地把 huobao 的 agent 与多模态经验吸收进来，持续训练 agent、workflow、eval、multimodal 这四类核心能力。**

## 十四、一句话结论

当前最值得你优先投入的，不是“大而全的平台功能”，而是：
