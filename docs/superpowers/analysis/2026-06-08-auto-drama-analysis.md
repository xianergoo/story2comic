# auto_drama 独立分析

> 日期：2026-06-08 | 状态：已落盘 | 范围：当前主仓 `auto_drama`

## 一、项目定位

`auto_drama` 当前更准确的定位，不是完整的 AI 短剧生产平台，而是一个以长内容创作为中心的 AI 叙事生成底座。

它当前主要承载的是：

1. AI 小说生成
2. 大纲规划
3. 章节级异步写作
4. 章节级流式正文展示
5. 章节完成后的漫画/插画扩展生成

从产品形态看，它已经从最初的服务端模板渲染，演进为：

- Go API
- Vue 3 SPA
- SSE 实时事件流

所以它现在最有价值的身份是：

**一个偏小说/漫画上游的 AI 内容生成原型底座。**

## 二、技术栈与运行方式

### 后端

主要技术栈：

- Go
- Gin
- GORM
- SQLite
- gin-contrib/sessions
- SSE
- 内存 channel 任务队列

运行特点：

- 单二进制服务
- 默认本地 SQLite 数据库
- 默认本地图片目录
- 通过 `.env` 加载配置
- 支持本地直接启动，部署门槛低

### 前端

主要技术栈：

- Vue 3
- Vite
- Pinia
- Axios
- EventSource

运行特点：

- 与后端分离构建
- 通过 `/api/v1` 对接后端
- 使用 Vite 代理进行本地开发联调

## 三、核心业务模型

当前项目的业务骨架比较清楚，主要围绕以下对象组织：

1. `User`
2. `AIConfig`
3. `Novel`
4. `Outline`
5. `Chapter`
6. `ComicPage`
7. `AgentTask`
8. `Checkpoint`

其中真正构成主生产链路的是：

- `Novel`
- `Outline`
- `Chapter`
- `ComicPage`

也就是说，这个系统当前本质上是：

**以作品为中心、以章节为主要生成单元的内容创作系统。**

`AgentTask` 与 `Checkpoint` 已经出现，但更像未来能力预埋，而不是当前主链路核心。

## 四、后端架构特征

### 1. 初始化结构较清楚

当前后端已经完成一轮初始化重构，主流程大致是：

1. 加载配置
2. 打开数据库
3. 执行迁移
4. 构建 services
5. 构建 runtime
6. 构建 router
7. 启动 HTTP 服务
8. 接入 signal + shutdown

这使得当前项目已经摆脱了“所有依赖混在 main.go”的原型状态。

### 2. handler / service 分层明确

`handler` 负责：

- 参数解析
- session 读取
- HTTP 响应
- 快照接口输出

`service` 负责：

- 大纲生成
- 章节生成
- 漫画生成
- 小说生成流程协调
- AgentTask / Checkpoint 状态管理

### 3. 任务系统是关键支撑层

当前任务系统采用轻量方案：

- 文本写作队列
- 图片/漫画队列
- 每队列 worker
- channel 驱动异步处理

它的优点是简单、好理解、单机可运行；缺点是：

- 无持久化恢复
- 无分布式能力
- 无强任务治理体系

### 4. SSE 事件体系已经形成正式协议雏形

当前结构化事件类型包括：

- `novel_status`
- `progress_summary`
- `chapter_status`
- `chapter_stream`
- `outline_stream`
- `comic_status`
- `log`
- `error`

这是当前项目非常值钱的一层，因为它意味着：

- 生成过程可见
- 页面可按事件局部刷新
- 流式文本与状态更新已统一协议化

### 5. Agent 目前仍属于“壳层能力”

当前 Agent 相关能力主要是：

- 任务创建
- 任务查询
- 任务取消
- checkpoint 查询
- checkpoint 更新

但它还没有真正成为主业务流程的智能执行中枢，因此现阶段更适合作为后续扩展基础，而不是作为现有核心卖点。

## 五、前端架构与交互主轴

当前前端页面比较克制，主要围绕以下路由：

1. 登录页
2. 注册页
3. 首页书架
4. 作品详情页
5. 章节页
6. AI 配置页

职责分工比较明确：

### 首页

- 展示作品总览
- 提供创建入口
- 提供继续/停止快捷操作

### 作品详情页

- 展示作品总状态
- 展示章节列表
- 展示事件流
- 提供继续/停止/重生成控制

### 章节页

- 展示单章节正文
- 展示实时正文流
- 展示漫画结果
- 提供章节级重生成与上下章导航

### AI 配置页

- 管理用户可用模型配置

前端目前最成熟的地方不是视觉，而是：

**围绕生成过程做出的实时体验组织。**

## 六、核心优点

### 1. 端到端闭环已经成立

从 AI 配置、作品创建、大纲、章节、漫画、SSE 到前端展示，已经形成一个完整可运行链路。

### 2. 对象层次清晰

`Novel -> Outline -> Chapter -> ComicPage` 关系明确，认知成本低，后续也容易重构映射。

### 3. 流式体验完成度高于一般原型

不是简单的任务开始/结束提示，而是已经具备：

- 流式正文
- 作品级状态
- 章节级状态
- 进度汇总
- 快照回拉

### 4. 轻量单机原型效率很高

适合快速试验、快速修复、快速迭代。

### 5. 前后端协议开始结构化

这对后续平台化和跨项目整合非常重要。

## 七、明显局限

### 1. 仍是“小说驱动”而不是“短剧驱动”

缺少短剧平台真正关键的对象：

- 场次
- 镜头
- 分镜
- 配音
- 视频片段
- 合成时间线
- 成片资产

### 2. 任务系统仍偏原型级

当前内存队列不适合复杂长流程、大规模任务恢复和平台级调度。

### 3. Agent 还不是流程核心

虽然有 AgentTask / Checkpoint，但尚未真正驱动主业务流程。

### 4. 数据模型更偏结果存储，不偏生产资产管理

很多内容仍以 JSON 或长文本形式存在，更适合灵活试验，不利于复杂资产编排。

### 5. 前端还不是工作台形态

当前仍是：

- 书架页
- 详情页
- 章节页

而不是：

- 项目生产台
- 任务面板
- 审核工作台
- 资产时间线

## 八、从 AI 短剧生成平台视角的核心价值

如果从后续平台演进角度看，`auto_drama` 最值得保留的不是“小说”这个名字，而是以下三层能力。

### 1. 结构化生成流程

- 先规划
- 再按单元生成
- 子任务串联推进

这与短剧生产流程天然兼容，只是单元粒度需要从章节迁移到场次/镜头。

### 2. 结构化实时反馈协议

当前 SSE 协议已经证明：

- 过程可见
- 当前步骤可见
- 正文可流式展示
- 断线后可回拉快照

这非常适合迁移到未来的剧本、分镜、配音、视频等生产链路。

### 3. 轻量但完整的 AI 生产闭环

它已经具备一个内容平台最基本的闭环意识：

- 配置模型
- 发起生成
- 观察过程
- 查看结果
- 重试/重生成

## 九、后续适合迁移/扩展的方向

### 1. 从章节模型迁移到场次/镜头模型

建议后续逐步映射为：

- `Novel` -> `Project` / `DramaProject`
- `Outline` -> `StoryPlan` / `ScriptBible`
- `Chapter` -> `Scene`
- `ComicPage` -> `ShotAsset` / `StoryboardFrame`

### 2. 升级任务系统

后续需要从内存队列演进到：

- 可持久化任务表
- 可恢复 worker
- 明确状态机
- 重试/取消/超时机制

### 3. 让 Agent 从“任务外壳”升级为“执行中枢”

当前预埋的 AgentTask / Checkpoint 很适合进一步演进成：

- 剧情策划 agent
- 分镜 agent
- 角色一致性 agent
- 配音 agent
- 审核 checkpoint 流

### 4. 把当前实时协议升级为平台统一事件总线

当前 SSE 协议是一个很好的起点，后续可以扩展成覆盖全平台的统一事件模型。

## 十、一句话结论

`auto_drama` 不是成熟的 AI 短剧生成平台，但它已经建立了一个很有价值的底座：

**它把“规划 -> 异步执行 -> 流式反馈 -> 结果查看 -> 重生成”这条 AI 内容生产主链路，做成了一个轻量、清晰、可继续演化的原型系统。**
