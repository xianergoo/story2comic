# AI 开发工程师面试底牌与项目映射

> 日期：2026-06-08 | 状态：已落盘 | 关联项目：`auto_drama`

## 一、本文目标

本文不是泛泛而谈“怎么准备 AI 面试”，而是结合当前主项目 `auto_drama`，明确回答三个问题：

1. 从后端转 AI 开发工程师，真正有价值的面试底牌是什么
2. 当前项目里哪些经历最值得沉淀成面试故事
3. 结合当前要做的文生图改进，还应该额外做哪些设计，才能在后续面试中更有说服力

## 二、什么叫“面试底牌”

面试底牌不是：

- 会调某家模型 API
- 会写 prompt
- 会用某个 agent 框架
- 会让 AI 帮忙生成代码

真正的底牌是：

### 1. 你能独立做出技术判断

例如：

- 为什么这里该用 workflow，而不是 agent
- 为什么这里该拆成 tool，而不是继续堆 prompt
- 为什么这里需要人工确认节点
- 为什么这个任务不能只靠更强模型解决

### 2. 你做过真实系统，并知道它是怎么坏的

例如：

- 模型输出不稳定
- 状态不一致
- tool 调用失败
- prompt 漂移
- 上下文截断
- 长链路累计误差

### 3. 你有一套可复用的 AI 工程分析框架

例如：

- 如何拆 agent 边界
- 如何做 workflow 编排
- 如何设计 tool 输入输出
- 如何做 tracing / eval
- 如何做人工介入和恢复

## 三、面试中最值得建立的六张底牌

## 1. Agent 与 Workflow 的边界判断

这是最容易拉开层次的一张底牌。

你需要能明确讲出：

- 固定步骤、规则清楚、结果可枚举的，优先 workflow
- 需要理解开放文本、选择工具、容忍不确定输出的，才考虑 agent
- 多 agent 不是更高级，而是复杂度更高

如果你只能说“我用了 agent 框架”，这个信号很弱。

如果你能说“我为什么不用 agent”，这个信号往往更强。

## 2. Tool Calling 设计能力

你需要能讲清：

- tool 为什么这样拆
- tool 的输入输出如何结构化
- tool 错误怎么分层
- 哪些 tool 必须幂等
- tool 返回是给人看还是给 agent 继续消费

这类内容在 `auto_drama` 后续演进里非常适合落地，因为文生图链路天然会涉及：

- 文本分析 tool
- prompt 生成 tool
- 图片生成 tool
- 结果评估 tool

## 3. Prompt 版本化与结构化输出能力

你要能把 prompt 当成系统接口来讲，而不是文案技巧。

需要具备的判断包括：

- prompt 如何分层
- prompt 如何模板化
- prompt 改动如何对比
- 输出为什么必须结构化
- prompt 是否依赖特定模型特性

如果你能把 prompt 管理讲成工程问题，而不是语言艺术问题，你在面试中的可信度会高很多。

## 4. Eval / Tracing / Observability 能力

这是大量候选人最弱的一张牌，但恰恰最容易拉开差距。

你需要能讲出：

- 如何记录输入输出
- 如何记录 prompt/version
- 如何记录 tool 调用链路
- 如何看每一步耗时和失败原因
- 如何建立样本集
- 如何做回归验证

面试里如果你能明确说：

“我不会只看 demo 效果，我会保留样本集、记录 prompt 和 tool 轨迹，并做最小评估闭环。”

这是很有分量的表达。

## 5. Context Engineering 与 RAG 基础能力

即使当前项目重点不是 RAG，也建议必须补这块。

你至少要能讲清：

- 为什么需要检索
- 如何切 chunk
- 如何做召回与精排权衡
- 如何管理上下文窗口
- 什么情况下不该检索

这部分在很多 AI 岗位里都是高频考点。

## 6. Failure Mode 思维

你必须能快速分析 AI 系统会怎么坏。

例如：

- 模型输出格式错
- tool 参数错
- 状态流转错
- checkpoint 不可恢复
- prompt 在不同模型上漂移
- 长链路误差放大
- 人工确认点缺失导致错误继续传播

会分析失败模式的人，比“会接模型”的人更像 AI 工程师。

## 四、结合 `auto_drama`，哪些经历最适合变成面试故事

## 1. 你已经做过“实时 AI 生成体验”的结构化设计

这是一个很好的故事点。

你可以讲：

- 为什么单纯轮询不够
- 为什么要把 SSE 结构化
- 为什么要区分作品级、章节级、正文流级事件
- 为什么前端要同时维护快照与流式状态

这个故事可以体现：

- 产品理解
- 实时系统设计能力
- 面向 AI 任务的状态建模能力

## 2. 你已经做过“从模板站点到 API + SPA”的架构收口

这说明你不是只会写功能，而是能主动为后续 AI 产品演进整理底座。

这个故事可以讲：

- 为什么后端只保留 API / SSE / session / static image
- 为什么前端改成独立 Vue SPA
- 这样做如何更适合后续引入 agent 和复杂实时交互

## 3. 你已经碰到了“任务流 + 状态 + 可见化”的核心问题

这本身就是 AI 工程问题，而不只是普通后端问题。

你可以讲：

- 如何让生成过程可见
- 如何处理停止/继续/重生成
- 如何把结果和过程分开建模

## 4. 你已经开始做“跨项目吸收能力”的工程判断

这一点在面试里非常有价值。

你不是机械复制 huobao，而是在判断：

- 哪些 agent 思想值得吸收
- 哪些多模态能力值得保留
- 为什么当前阶段不直接整体迁移

这能体现你有架构判断，而不是只会搬代码。

## 五、为了让后续面试更有底牌，当前项目应该额外补哪些设计

这一部分最关键。

如果只继续做“文生图功能”，但不补下面这些设计，你的项目更像“AI 功能项目”；如果补上这些设计，它才更像“AI 工程项目”。

## 1. 最小 Agent 分层设计

建议不要直接做大而全 agent，而是明确拆出最小角色。

建议优先拆：

1. `story_analyzer`
2. `image_prompt_generator`
3. `result_reviewer` 或 `consistency_checker`

你需要额外设计的是：

- 每个 agent 的输入结构
- 每个 agent 的输出结构
- 每个 agent 允许调用哪些 tool
- 每个 agent 的失败结果如何回传

这会直接变成你面试时的“agent 边界设计”案例。

## 2. Tool Schema 与契约设计

当前如果只是直接在 service 里调用生成逻辑，面试价值有限。

更值得你补的是一层明确的 tool 契约，例如：

- `analyze_story`
- `extract_characters`
- `build_image_prompt`
- `generate_image`
- `evaluate_image_result`

每个 tool 都应考虑：

- 输入 schema
- 输出 schema
- 可重试错误
- 不可重试错误
- 日志字段

这层设计一旦补上，你就不只是“有功能”，而是“有 agent 工程接口”。

## 3. Prompt Version 与输出结构设计

建议你尽早补一层最小能力：

- prompt 模板命名
- prompt 版本号
- 当前调用使用的 prompt 记录
- 输出结构化解析

你不一定一开始就做完整 prompt 管理平台，但至少要让自己后面能说：

“我有意识地把 prompt 当成系统接口，而不是把它散写在业务代码里。”

## 4. Execution Trace 设计

这块非常值得补。

你应该额外设计一层最小执行轨迹，至少记录：

1. 请求输入摘要
2. 使用的模型
3. 使用的 prompt 版本
4. 调用了哪些 tool
5. 每一步输出摘要
6. 每一步耗时
7. 最终结果与失败原因

这层能力会让你在面试里立刻从“做了个 AI demo”升级成“做了一个可观测 AI 系统”。

## 5. Human-in-the-loop 设计

建议你不要把“人工复核”只停留在文档层，也应该在产品设计里提前预留。

即使当前只是文生图，也可以补一个最小人工节点，例如：

- 允许用户确认抽取出的角色/场景
- 允许用户在生成前修改 prompt
- 允许用户标记结果好/差

这样你后面在面试里就能讲：

“我没有把 AI 当成黑盒自动化，而是预留了人工确认和反馈闭环。”

## 6. Minimal Eval 设计

如果你后续想有更强底牌，一定要补最小评估能力。

建议至少设计：

1. 样本 case 列表
2. 生成结果打分字段
3. 失败原因分类
4. prompt 对比记录

这不需要一开始就很复杂，但必须有雏形。

因为没有这层，你很难在面试里证明自己做的是“可迭代 AI 系统”，而不只是“调用了几次模型”。

## 六、结合当前文生图改进，建议优先补的设计顺序

如果结合你当前项目节奏和目标，我建议优先级如下。

## 第一优先级

1. 文生图主链路可交互闭环
2. 最小 agent 角色拆分
3. tool schema 契约
4. execution trace

这四项是最能同时提升产品可用性和面试底牌的。

## 第二优先级

1. prompt version 管理
2. 人工确认点
3. 最小结果评估机制

这三项会明显提高你的“AI 工程化”含量。

## 第三优先级

1. 更复杂的 checkpoint / resume
2. 更复杂的多 agent 协作
3. 更完整的多模态编排

这些值得做，但不应先于前两级。

## 七、你后续应该怎么讲这些项目经历

你后续要尽量避免把项目讲成：

- 我做了一个 AI 项目
- 我接了模型生成图片
- 我用了 agent

更强的讲法是：

### 1. 讲判断

例如：

- 为什么这一步不用 agent
- 为什么这里必须结构化输出
- 为什么这里需要人工反馈

### 2. 讲系统

例如：

- 我怎么把一个开放式生成任务拆成可观测链路
- 我怎么设计实时事件协议
- 我怎么记录 prompt、tool、结果和失败原因

### 3. 讲失败和修正

例如：

- 某次设计为什么太理想化
- 某个 prompt 为什么不稳定
- 某步为什么必须降级成 deterministic step

面试官通常更相信“真实取舍和踩坑”，而不是“功能做得很多”。

## 八、建议你后续主动补的知识点

结合当前项目，建议你主动补这些内容：

1. structured output 与 JSON schema
2. tool calling 设计模式
3. prompt versioning 思路
4. tracing / eval 方法
5. context engineering
6. RAG 基本设计
7. checkpoint / resume 设计
8. human-in-the-loop 模式

这些内容一旦和 `auto_drama` 项目实践绑定，就会比单纯刷面经强很多。

## 九、最终建议

如果你的目标是未来 AI 开发工程师面试中有更多底牌，那么当前最正确的方向不是继续堆“AI 功能数量”，而是：

**把 `auto_drama` 的当前文生图改进，主动做成一个带有 agent 分层、tool 契约、prompt 版本、执行轨迹、人工反馈和最小评估闭环的 AI 工程样板。**

这样你后面讲的就不只是“我做了 AI 功能”，而是：

**我把一个开放式 AI 任务做成了可交互、可观测、可迭代、可复盘的工程系统。**

## 十、一句话结论

真正能让你在 AI 开发工程师面试里更有底牌的，不是你用了多少 AI，而是：

**你是否能证明自己具备把不稳定 AI 能力工程化的判断、设计、观测、评估和迭代能力。**
